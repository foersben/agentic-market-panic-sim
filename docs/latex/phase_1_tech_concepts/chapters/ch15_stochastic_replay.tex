\chapter{Stochastic Replay and Double Buffering}
\label{ch:stochastic_replay}

A major challenge in multi-agent generative modeling is debugging. When a market panic occurs at tick 45,000 driven by the emergent interactions of 400 LLM agents, reproducing that exact scenario to fix a bug in the matching engine is nearly impossible. Generative AI is inherently non-deterministic. This chapter details the strict mandates established in \texttt{01-stochastic-engine-and-replay.md} for capturing and analyzing emergent panics via Zarr buffers.

\section{The Non-Determinism Problem}

Even if the PRNG (Pseudo-Random Number Generator) seeds for the engine's internal mathematics are hard-locked, the cognitive outputs of the 400 micro-agents are subject to massive stochastic variance. A slight change in GPU temperature might alter the floating-point math of the LLM inference just enough to shift an agent's output from "buy" to "sell."

If the simulation crashes, the engineer cannot simply restart the script and expect the identical sequence of 45,000 ticks to unfold. The "Butterfly Effect" will cause the timeline to diverge within milliseconds. 

\section{Double Buffering and Immutability}

To solve this, AMPS enforces a strict \textbf{Double Buffering} paradigm within its ECS arrays, a technique borrowed directly from high-performance graphics rendering.

During Tick $T$:
\begin{enumerate}
    \item \textbf{Read Layer:} All Numba systems and agents read the state of the market exclusively from a locked, immutable \texttt{Read Buffer}.
    \item \textbf{Write Layer:} All state transitions, executed orders, and agent cognitive intents are written exclusively to a separate \texttt{Write Buffer}.
\end{enumerate}

At the end of the tick, the \texttt{Write Buffer} is swapped to become the new \texttt{Read Buffer} for Tick $T+1$. This architecture guarantees that the order of execution within a single tick cannot create race conditions or alter the state for other agents executing concurrently.

\section{Zarr Telemetry Buffers}

Because the \texttt{Write Buffer} captures the absolute, final, immutable truth of every entity's state at the end of the tick, AMPS streams this buffer directly to disk.

Instead of writing to a slow SQL database or an inefficient JSON file, the simulation utilizes \textbf{Zarr} \cite{zarr2023dev}. Zarr is a cloud-native, chunked, compressed, N-dimensional array storage format. Because the ECS state is already formatted as dense NumPy arrays, streaming them to Zarr incurs almost zero serialization overhead.

\section{Engine Bypass for Deterministic Replay}

The core mandate of the AMPS replay system is that \textbf{Playback must read historical Zarr matrices directly, bypassing all engine loop logic.}

When a researcher wishes to investigate the flash crash at tick 45,000, they load the Zarr file into the AMPS UI. The UI does not initialize the Numba matching engine, nor does it invoke the Macro Orchestrator God Agent. It merely renders the raw NumPy arrays stored in the Zarr chunks. 

This guarantees 100\% pixel-perfect deterministic replay of the crash, allowing engineers to step backward and forward through time, inspecting the exact Limit Order Book state and the specific cognitive intent of any micro-agent at the exact microsecond the panic crystallized.
