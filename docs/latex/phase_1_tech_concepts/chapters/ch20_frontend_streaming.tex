\chapter{Front-End UI Architecture: Apache Arrow IPC Streaming \& Wasm-Accelerated Analytics via FINOS Perspective}
\label{ch:frontend_streaming}

A high-performance financial simulation engine capable of processing 1,000,000 agents at over 100,000 Ticks Per Second requires an observation pipeline capable of rendering high-frequency microstructural chaos in real time without introducing backpressure into the matching engine. Traditional Single Page Applications (SPAs) built on React or Vue introduce massive client-side state reconciliation overhead, which collapses when bombarded with thousands of state updates per second. 

This chapter outlines the unified AMPS front-end and telemetry streaming architecture: combining server-side draft state management, Apache Arrow IPC streaming over WebSockets, WebAssembly-accelerated real-time analytics via FINOS Perspective \cite{finos_perspective}, and Redis PubSub process decoupling. Rather than constructing bespoke binary serialization protocols and custom GPU canvas shaders, AMPS frames FINOS Perspective as a drop-in replacement that natively extends the simulation core's existing Apache Arrow memory infrastructure (Chapters \ref{ch:zero_copy_ipc} and \ref{ch:multi_patch_harvesting}) directly into the client browser.

\section{The Failure of Client-Side Virtual DOMs}

In a conventional web dashboard, server backends serialize state updates into JSON and transmit them over standard WebSockets. The client-side JavaScript engine parses each incoming JSON string, updates a centralized state tree (e.g., Redux), executes Virtual DOM diffing, and schedules DOM reflows.

At high-frequency simulation rates, this architecture causes immediate catastrophic degradation:
\begin{enumerate}
    \item \textbf{JSON Parsing \& Memory Pressure:} Parsing multi-megabyte JSON payloads at 60 Hz exhausts the browser's V8 garbage collector, producing severe frame-rate drops and tab freezing.
    \item \textbf{Layout Thrashing:} Mutating the browser's Document Object Model (DOM) to update order book depth ladders or price charts forces continuous recalculation of geometric styles, locking the browser's main UI thread.
\end{enumerate}

Similarly, attempting to use server-side rendering libraries like HTMX to swap tabular HTML markup at high frame rates fails due to layout thrashing. Consequently, AMPS enforces a complete separation: HTMX is utilized strictly for low-frequency configuration and draft state lifecycle management, while high-frequency telemetry is streamed as continuous Apache Arrow Record Batches directly into a WebAssembly-compiled data grid (FINOS Perspective), bypassing the DOM while maintaining zero-copy semantics.

\section{Arrow IPC WebSockets and Wasm Hardware Acceleration}

To eliminate JSON serialization and DOM layout overhead, AMPS executes all high-frequency telemetry streaming through binary WebSockets carrying Apache Arrow IPC streams directly into FINOS Perspective's WebAssembly execution environment. This architecture establishes a seamless zero-copy and zero-deserialization pipeline spanning from the backend's \texttt{PyCapsule} Arrow pointers to the frontend's Wasm linear memory.

\subsection{Zero-Copy Apache Arrow IPC Serialization}

In naive financial visualization systems, developers often resort to packing numerical metrics into ad-hoc binary C-structs. While this avoids text-based JSON encoding, it introduces severe architectural brittleness: the client must maintain synchronized byte-offset definitions and manually parse fields using JavaScript \texttt{DataView} or typed array slice offsets. Any schema drift -- such as adding an order identifier or higher-order book depth levels -- requires error-prone manual refactoring across both C/Python serialization kernels and JavaScript client decoding logic.

To achieve strict high-frequency throughput without custom serialization fragility, AMPS standardizes its streaming transport entirely on the \textbf{Apache Arrow IPC streaming protocol} \cite{apache_arrow_c_data}, unifying the UI layer with the IPC mechanisms already deployed in Chapter \ref{ch:zero_copy_ipc} (shared memory buffers) and Chapter \ref{ch:multi_patch_harvesting} (offline trajectory record batches).

When the matching engine completes a simulation tick, the contiguous NumPy arrays capturing top-of-book depth ladders, Order Flow Imbalance (OFI), transaction prices, and agent state metrics are encapsulated as zero-copy \texttt{pyarrow.RecordBatch} objects via the Arrow C Data Interface (\texttt{PyCapsule} pointers). Rather than executing costly memory reallocations or transpositions, the backend leverages \texttt{pyarrow.ipc.RecordBatchStreamWriter} to emit encapsulated Arrow IPC stream chunks directly into contiguous byte buffers. 

Because Apache Arrow defines an identical columnar binary memory layout across all programming language runtimes, these binary IPC chunks require zero data transformation when streamed over WebSocket frames. When received by the browser, the raw WebSocket payload arrives as an \texttt{ArrayBuffer} representing a valid Arrow Record Batch, which FINOS Perspective consumes directly without deserialization.

\subsection{Wasm Table Ingestion and Perspective Virtualized Rendering}

Writing and maintaining custom WebGL vertex and fragment shaders for client-side financial visualization introduces substantial engineering overhead. Custom GPU shaders require manual management of vertex buffer objects (VBOs), projection matrices, and tessellation routines for order book ladders, all while remaining decoupled from interactive analytical operations like dynamic filtering, column sorting, and multi-dimensional aggregation.

AMPS replaces the custom shader stack with \textbf{FINOS Perspective} \cite{finos_perspective}, an open-source streaming data engine and visualization component purpose-built for financial trading desks. Perspective executes via a four-tier architecture:
\begin{enumerate}
    \item \textbf{C++ WebAssembly Query Engine (\texttt{perspective.wasm}):} Perspective's core analytical engine is authored in C++ and compiled to WebAssembly via Emscripten. The Wasm runtime executes entirely inside a dedicated HTML5 Web Worker thread, completely isolating computationally intensive tabular aggregations, multi-index pivots, and hyper-cube index calculations from the browser's UI thread.
    \item \textbf{Native Arrow Ingestion via \texttt{table.update()}:} When the WebSocket client receives an Arrow IPC buffer, it invokes Perspective's table interface:
    \begin{equation}
        \texttt{table.update(arrayBuffer)}
    \end{equation}
    Perspective's C++ core directly traverses the Apache Arrow columnar chunks in Wasm linear memory. Because Arrow's binary representation matches Perspective's internal columnar layout, ingestion executes in sub-millisecond time without creating JavaScript objects or triggering V8 garbage collector pauses.
    \item \textbf{Virtualized DOM Data Grids (\texttt{@perspective-dev/viewer-datagrid}):} For tabular displays -- such as 20-level LOB depth ladders, order blotters, and institutional agent inventories -- Perspective mounts a high-performance virtualized grid. Only the DOM elements currently visible within the viewport are created and mutated, achieving stable 60 FPS updates even when streaming hundreds of thousands of simulation updates.
    \item \textbf{Integrated Canvas/WebGL Charting (\texttt{@perspective-dev/viewer-charts}):} To visualize continuous market dynamics, Perspective integrates hardware-accelerated charting powered by D3FC and WebGL out of the box. The engine natively transforms streaming Arrow columns into real-time Limit Order Book depth curves, Order Flow Imbalance histograms, and multi-agent PnL trajectories. Researchers can interactively pivot, slice, and cross-filter high-dimensional agent telemetry directly in the browser without writing a single line of shader code.
\end{enumerate}

\section{I/O Decoupling via Redis PubSub}

Directly streaming WebSocket payloads from the simulation core creates a dangerous vulnerability: \textbf{TCP Backpressure}.

The Numba matching engine is pinned to host Gracemont E-cores to preserve microsecond execution determinism. If the simulation loop wrote directly to a client WebSocket, an intermittent Wi-Fi latency spike or network stall on the client would cause the operating system's TCP socket buffer to fill. The kernel would block subsequent \texttt{write()} syscalls, instantly halting the core financial matching engine and destroying FIFO price-time priority simply because an external observer experienced network jitter.

To eliminate this vulnerability, AMPS decouples the core engine from external network I/O using local \textbf{Redis Publish/Subscribe (PubSub)}:

\begin{enumerate}
    \item \textbf{Fire-and-Forget Publisher:} At the end of each tick, a dedicated telemetry thread transmits the serialized Apache Arrow IPC record batch to a local Redis instance over a Unix domain socket (\texttt{amps\_telemetry}). Because Unix domain sockets operate entirely in host memory, this publish operation executes in under 50 microseconds and never blocks the engine.
    \item \textbf{Asynchronous Multiplexing Subscriber:} The FastAPI web server \cite{selivanov2016uvloop}, running in an isolated process on dedicated cores, subscribes to Redis. FastAPI fans out the binary stream to arbitrary connected WebSockets.
    \item \textbf{Stale Packet Dropping:} If an individual client connection buffers or lags, FastAPI automatically drops stale packets for that specific subscriber, completely isolating both the Redis queue and the matching engine from network congestion.
\end{enumerate}

\section{Draft State Management and Scenario Loading}

Prior to executing a scenario, the user configures initial parameters -- such as macro narrative shocks, liquidity distributions, and agent archetype ratios -- through interactive HTML forms.

To maintain strict validation without mutating live simulation memory, AMPS implements a \texttt{DraftService} pattern:
\begin{enumerate}
    \item Parameters are edited in the browser via HTMX, mutating an isolated server-side \texttt{DraftState} instance via \texttt{POST} endpoints.
    \item When the operator commits the scenario, a \texttt{POST /api/scenario/load-draft} call executes.
    \item The server validates all invariants, locks the \texttt{DraftState}, pre-allocates the contiguous NumPy double-buffers (Chapter \ref{ch:data_oriented_design}), pins the execution threads via \texttt{cgroups v2} (Chapter \ref{ch:hardware_topography}), and initializes the live simulation loop.
\end{enumerate}

Through this multi-tier front-end and telemetry architecture, AMPS provides zero-latency real-time observability while guaranteeing absolute microsecond determinism in the core financial engine.
